## 2. Что делает приложение

Это мобильная веб-страница, не APK. Пользователь на Android наводит заднюю камеру телефона на телевизор/проектор с игрой. Страница вырезает вручную задаваемую зелёной рамкой ROI, распознаёт попавшие туда русские субтитры и читает их через Android browser SpeechSynthesis.

Основные части:
- Камера через getUserMedia (HTTPS, Chrome/совместимый Android-браузер).
- Пользователь перемещает и меняет размер ROI пальцем.
- Canvas crop + preprocessing.
- OCR PaddleOCR.js в Web Worker.
- Русская модель PaddleOCR East Slavic.
- Озвучка через SpeechSynthesis, выбор русского голоса, скорость/громкость.
- Очередь, дедупликация, стабилизация реплик.
- Страница размещена в GitHub Pages через Vite + GitHub Actions.

Требования пользователя: всё локально/бесплатно, без платных OCR API. Нельзя предлагать облачный платный OCR как основное решение.

## 3. Текущая известная рабочая техническая база

Последняя подтверждённая пользователем стабильная модельная связка:
- `@paddleocr/paddleocr-js` версии `0.4.2`.
- Детекция: `PP-OCRv5_mobile_det`.
- Распознавание: `eslav_PP-OCRv5_mobile_rec` (East Slavic, для русского/украинского/белорусского).
- Архив recognition-модели `models/eslav_PP-OCRv5_mobile_rec.tar` создаётся в CI из официальных model assets; он не обязательно лежит в Git в исходном виде.
- Рабочий режим OCR после отката v0.50: штатный ONNX Runtime из PaddleOCR.js, backend `wasm`, `numThreads: 1`, `simd: true`.
- Preprocessing ROI в текущем коде: crop камеры, увеличение примерно 1.8×, grayscale + contrast(1.35).
- Текущий ROI хранится через HTML range inputs и CSS guide overlay.
- Распознавание выполняется последовательно в scanLoop; один OCR predict завершается до следующего. Текущий cooldown в v0.51 — 60 ms.
- Сборка Vite, base path `/Gta6Voice/`.

Важное доказательство: пользователь подтвердил, что после возврата к штатному WASM OCR в версии 0.50 **распознавание снова работает, и озвучка тоже работает**. Сохраняй это состояние. Не повторяй неудачные GPU эксперименты без диагностики.

## 4. История проблем и неудачных экспериментов — обязательно учти

- Ранние версии использовали Tesseract.js. После нескольких медленных/нестабильных итераций пользователь одобрил переход на PaddleOCR.
- v0.35: миграция на PaddleOCR.js + East Slavic PP-OCRv5 recognition. Пользователь сказал, что распознавание стало нормальным. Это важный ориентир.
- v0.36: поправили FIFO очередь и убрали удаление старых фраз, но позже стало ясно, что неограниченная очередь приводит к чтению уже прошедшего диалога.
- v0.37–v0.38: эксперимент с лимитом detector side length и диагностикой детекции/распознавания.
- v0.39–v0.43: попытки WebGPU с отдельной сборкой ONNX Runtime. На Android GPU provider показывался как webgpu, но детектор возвращал ноль текстовых областей или не находил видимые субтитры. В процессе была ошибка с версией ONNX Runtime и проблемы деплоя.
- v0.44–v0.48: меняли resize/модель детекции; PP-OCRv6 Tiny также не исправил проблему.
- v0.49: попытка самодельного гибрида WASM detector + WebGPU recognizer была некорректной. НЕ ВОЗВРАЩАТЬ эту реализацию.
- v0.50: убрали WebGPU shim/alias и вернули штатный PaddleOCR.js + WASM. Пользователь подтвердил: сканирование работает, озвучка работает.
- v0.51: изменяли стратегию озвучки/очереди. Пользователь сообщил основную цель: при быстрых репликах система отстаёт; двухстрочные субтитры могут повторяться; накопленная очередь читает старые реплики уже после того, как сюжет ушёл вперёд.

Не утверждай, что WebGPU ускоряет приложение, пока фактически не измерены и не подтверждены одновременно корректные детекция, распознавание и время на устройстве пользователя.

## 5. Текущая главная задача: реальное время и TTS queue policy

Пользователь описал три конкретные проблемы:
1. Реплики быстро меняются, OCR/TTS не успевают.
2. Двухстрочные субтитры могут произноситься дважды или по частям с повтором.
3. Очередь накапливается; голос затем последовательно проговаривает старые фразы, пока игровой сюжет уже ушёл далеко вперёд.

В v0.51 уже сделана первая попытка:
- очередь ограничена одним pending item помимо текущей активной фразы;
- новая независимая реплика заменяет старую ожидающую (latest-wins);
- реплика старше 3 секунд на старте воспроизведения пропускается;
- добавлено сравнение предыдущей и новой подписи для выявления расширения: например, первая строка «Я заняла это место», затем полный текст «Я заняла это место. Для кого?»; идея — прочитать только добавившуюся часть, не повторяя первую строку;
- короткое окно дедупликации;
- активный и ожидающий item содержат исходный caption text отдельно от произносимого fragment.
**Эта логика ещё не подтверждена пользователем на устройстве.** Нужно проверить edge cases: pending update, active speech, extension detection, same/partial captions, punctuation, OCR hallucination/correction, empty gap/repeat line.

### Что нужно сделать правильно

Не пытайся просто обрезать очередь и считать проблему решённой. Сформулируй и реализуй поведение как потоковый субтитровый reader:

- В каждый момент есть текущий caption-кандидат (может обновляться на следующих OCR проходах), последняя подтверждённая фраза, текущая активная TTS реплика и максимум одна ожидающая следующая фраза.
- Новый OCR результат может быть:
  - тот же caption;
  - уточнение/исправление уже видимой строки;
  - продолжение/добавление второй строки;
  - новая отдельная реплика;
  - пустой ROI/субтитр исчез.
- Две строки одного экранного субтитра — это обычно одна реплика, а не две независимые реплики. Используй координаты полигонов/строк и короткое окно temporal grouping, не склеивай разные диалоги вслепую.
- Если OCR сначала увидел первую строку, а в следующем проходе получил обе строки, не произноси верхнюю строку повторно. Лучше подождать короткое стабилизирующее окно, затем произнести целую подпись, пока она ещё актуальна. Но не вводи такую большую задержку, которая потеряет короткие реплики.
- Если во время TTS возникает новый самостоятельный caption, ожидающую старую реплику можно заменить новой, но не следует бесконечно прерывать уже звучащую фразу на каждом OCR фрейме.
- Старые pending captions должны протухать по возрасту. Не зачитывай устаревший диалог.
- Не позволяй частично распознанному тексту с мелкими OCR исправлениями создавать дубли.
- Учитывай, что SpeechSynthesis произносит текст медленнее, чем OCR может его получать. Если скорость TTS объективно меньше скорости смены субтитров, выбери и объясни компромисс: latest-wins, короткое объединение новых частей, ускорение речи в разумном диапазоне или пропуск просроченного pending. Не обещай абсолютную синхронизацию, физически невозможную при более длинной TTS, чем длительность субтитра.
- Очередь не должна расти без ограничения.
- Показывай в диагностике не только OCR ms, но и возраст фразы до начала TTS, число pending, время active speech и dropped/stale count. Диагностика не должна сама замедлять основной loop.

### Архитектурные улучшения для рассмотрения (только после профилирования)

- Разделить OCR inference и caption/TTS controller логически, не обязательно по потокам.
- Сравнить время подготовки crop, detector, recognition, parsing, stabilization и TTS start delay.
- Исследовать Android getUserMedia frame rate/resolution. Не менять capture resolution или scale вслепую: пользователь подтвердил, что распознавание важно не ухудшить.
- Рассмотреть уменьшение области ROI, адаптивное изменение частоты сканирования, ROI canvas preprocessing, но сравнивать реальные метрики.
- Не создавать второй параллельный OCR predict на одной модели/worker: он может перегрузить CPU и увеличить latency.
- Не запускать второй OCR на каждый кадр и не делать инверсию/бинаризацию как безусловный дополнительный проход — прежние варианты сильно тормозили.

## 7. Стиль работы и общения с пользователем

Пользователь говорит по-русски, предпочитает прямой неформальный стиль. Он раздражается, когда его просят повторно делать уже выполненные тесты, когда ему предлагают очевидные действия вместо анализа, или когда ассистент обещает результат без подтверждения.

Поэтому:
- Не заставляй повторно проверять уже известные вещи.
- Не обвиняй пользователя в неправильном наведении камеры без оснований.
- Не делай вид, что проблема решена, пока пользователь не подтвердил.
- Сначала изучай фактические файлы и диагностику, потом предлагай изменения.
- Вноси конкретные правки и сообщай, какие файлы и что изменено.
- Не меняй движок, модель, preprocessing и UI одновременно.
- Не предлагай другой голос до решения latency/queue issue.
- Не задавай много вопросов: обычно достаточно одного скриншота/одного контрольного теста, если он действительно нужен.

## 8. Точный следующий шаг

1. Прочитай весь актуальный app.js v0.51.
2. Нарисуй себе timeline: OCR result -> caption stabilization -> queue/pending -> utterance start -> utterance end.
3. Найди баги в current queue/captionRelation logic, прежде всего:
   - как extension «верхняя строка -> две строки» определяется по токенам;
   - не сравнивается ли caption с уже произнесённым/частично произнесённым текстом неправильно;
   - можно ли обновлять pending item без повторного создания/потери старого текста;
   - не превращает ли дедупликация законно повторённую реплику в пропуск;
   - что происходит, когда caption меняется, затем исчезает на 1–2 прохода, затем возвращается.
4. Предложи небольшую конечную модель состояний для caption controller и протестируй её на синтетических сценариях.
5. Только после этого меняй код. Не трогай проверенную WASM/OCR связку в первом проходе.
6. Добавь простые unit tests для caption comparison/queue policy, если возможно, чтобы эти баги не возвращались.

Главная цель: **голос должен следовать за текущим игровым диалогом, а не читать прошлые реплики с опозданием.** Надёжное распознавание, которое уже работает, нельзя потерять ради красивой цифры latency.
